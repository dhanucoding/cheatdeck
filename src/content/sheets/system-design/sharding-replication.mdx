## TL;DR
**Replication** = same data on many nodes. **Sharding** = different data on different nodes. Large systems use both.

## Replication
| Model | Writes go to | Trade-off |
|---|---|---|
| Leader-follower | One leader | Simple. Followers can lag, so reads may be stale |
| Multi-leader | Several leaders | Low write latency across regions, needs conflict resolution |
| Leaderless (quorum) | Any node | Tunable: `R + W > N` gives strong reads |

Sync replication is safe but slow. Async is fast but can lose recent writes on failover.

## Sharding strategies
| Strategy | Good | Bad |
|---|---|---|
| Range (by key range) | Efficient range scans | Hot spots (e.g. latest timestamps) |
| Hash | Even spread | Range scans touch all shards |
| Directory (lookup table) | Flexible placement | Lookup is a bottleneck/SPOF |

Pick a shard key with **high cardinality** and even access. Plan for resharding from day one, ideally with [consistent hashing](../consistent-hashing/).

## Costs to expect
- Cross-shard joins and transactions are hard or impossible.
- Rebalancing moves data while serving traffic.
- Operational complexity goes up a lot, so shard late.
